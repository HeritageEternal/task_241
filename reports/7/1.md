# Настраиваем ssh мне страшно после гитлаба

Работа выполнялась в виртуалке Arch Linux (`192.168.100.249`, основной юзер `xen`).

## 1–4. Базовые сведения об SSH-сервере

1. **Порт по умолчанию:** TCP **`22`**.
2. **Можно ли изменить порт:** да, директивой `Port <номер>` в конфиге SSH-сервера (например, `Port 2222`), после чего проверить конфиг через `sshd -t`, открыть новый порт в файрволе (если включен) и перезапустить службу.
3. **Служба входящих подключений:** **`sshd.service`** (демон OpenSSH `sshd`).
4. **Конфигурационный файл сервера:** **`/etc/ssh/sshd_config`** (в Arch Linux в нем подключен `Include /etc/ssh/sshd_config.d/*.conf`, поэтому локальные настройки удобно выносить в `/etc/ssh/sshd_config.d/99-lab.conf`).

### Резервная копия и проверка исходного конфига

Использованные команды:

```bash
sudo cp /etc/ssh/sshd_config /etc/ssh/sshd_config.bak
sudo grep -E '^(Include|Port|PermitRootLogin|MaxAuthTries|PasswordAuthentication)' /etc/ssh/sshd_config || true
sudo passwd -S root
```

Полученный результат:

```text
Include /etc/ssh/sshd_config.d/*.conf
root P 2026-09-26 -1 -1 -1 -1
```

Подтверждено, что `/etc/ssh/sshd_config` подхватывает файлы из `/etc/ssh/sshd_config.d/*.conf`, а у `root` в системе установлен пароль (`P`).

## 5–6. Подключение к серверу, временное разрешение `root` и почему постоянный root-login опасен

Для демонстрации временно прописано `PermitRootLogin yes` в `/etc/ssh/sshd_config.d/99-lab.conf`, перед перезапуском конфиг проверен командой `sudo sshd -t`, после чего выполнен вход под `xen` и под `root`.

Использованные команды:

```bash
sudo tee /etc/ssh/sshd_config.d/99-lab.conf > /dev/null <<'EOF'
PermitRootLogin yes
EOF
sudo sshd -t && echo "sshd config OK"
sudo systemctl restart sshd.service
ssh -o StrictHostKeyChecking=accept-new xen@192.168.100.249 'whoami && uname -n'
ssh root@192.168.100.249 'whoami && id'
```

Полученный результат:

```text
sshd config OK

xen@192.168.100.249's password:
xen
archlinux

root@192.168.100.249's password:
root
uid=0(root) gid=0(root) groups=0(root)
```

**Почему постоянный `PermitRootLogin yes` нежелателен:**
- имя `root` известно любому атакующему заранее - на него постоянно идут автоматические переборы паролей (брутфорс);
- при прямом входе под `root` теряется персональный аудит (непонятно, кто именно из админов зашел и что сделал);
- при компрометации учетных данных злоумышленник сразу получает максимальные права в системе. Безопаснее заходить под обычным юзером и повышать права через `sudo`.

## 6 (возврат), 7 и 8. Возврат `PermitRootLogin no`, настройка `MaxAuthTries` и создание `ssh-user`

Сразу после проверки вернули безопасное значение `PermitRootLogin no` и уменьшили допустимое число попыток аутентификации до `MaxAuthTries 3` (по умолчанию в OpenSSH - 6). Перед перезапуском конфиг проверен через `sudo sshd -t`. Затем создан юзер `ssh-user` и выполнен вход под ним.

Использованные команды:

```bash
sudo tee /etc/ssh/sshd_config.d/99-lab.conf > /dev/null <<'EOF'
PermitRootLogin no
MaxAuthTries 3
EOF
sudo sshd -t && echo "sshd config OK"
sudo systemctl restart sshd.service
sudo useradd -m -s /bin/bash ssh-user
sudo passwd ssh-user
ssh ssh-user@192.168.100.249 'whoami && id'
```

Полученный результат:

```text
sshd config OK

New password: 
Retype new password: 
passwd: password updated successfully

ssh-user
uid=1001(ssh-user) gid=1001(ssh-user) groups=1001(ssh-user)
```

Действующий фрагмент конфигурации `/etc/ssh/sshd_config.d/99-lab.conf` на этом этапе:

```text
PermitRootLogin no
MaxAuthTries 3
```

## 9, 10 и 13. Ограничение входа для `ssh-user` и проверка конфига до перезапуска

Вход по SSH для `ssh-user` ограничен директивой **`DenyUsers ssh-user`** в `/etc/ssh/sshd_config.d/99-lab.conf` - демон `sshd` отклоняет любые попытки подключения для этого юзера, при этом сама локальная учетная запись в системе не удаляется. Перед перезапуском службы конфигурация проверена командой `sudo sshd -t`.

Использованные команды:

```bash
sudo tee /etc/ssh/sshd_config.d/99-lab.conf > /dev/null <<'EOF'
PermitRootLogin no
MaxAuthTries 3
DenyUsers ssh-user
EOF
sudo sshd -t && echo "sshd config OK"
sudo systemctl restart sshd.service
ssh -o NumberOfPasswordPrompts=1 ssh-user@192.168.100.249 'whoami'
```

Полученный результат:

```text
sshd config OK

ssh-user@192.168.100.249's password: 
ssh-user@192.168.100.249: Permission denied (publickey,password).
```

Проверка `sudo sshd -t` прошла без ошибок (`sshd config OK`), после перезапуска `ssh-user` получает отказ `Permission denied`.

## 11–12. Назначение `known_hosts` и поиск ключа сервера

В файле `~/.ssh/known_hosts` хранятся **публичные ключи хостов (серверов)**, к которым юзер уже подключался. При каждом последующем подключении SSH-клиент сверяет ключ удаленного сервера с сохраненным - если ключ изменился, клиент предупреждает о возможной подмене сервера / атаке «человек посередине» (MITM).

Использованная команда:

```bash
ssh-keygen -F 192.168.100.249
```

Полученный результат:

```text
# Host 192.168.100.249 found: line 5 
192.168.100.249 ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIED855fNmgtSVFIj1cAREfWgzbXQYFPCwYCI05Ycm0bz
```
